# Mid-level front-end engineer — TalentLens bar (global)

TalentLens internal. Written by in-house recruitment experts. This is the default definition of a mid-level front-end engineer across mandates. It is not a client job description and it is not Kilometer-specific.

When a client file exists for the same level (for Kilometer: `front-end-mid-kilometer.md`), follow the client file. Specs there outrank both this document and the public posting.

## What mid-level means

About 3–5 years shipping production web. They can own a feature with product and design, write production React/TypeScript, review others, and mentor someone ramping on web.

They are not a junior who needs every ticket sliced to the hour. They are not staff or lead: they contribute to a frontend practice; they do not set org-wide architecture.

## Expected bar

- **UI:** Semantic HTML, modern CSS (layout, responsive, design-system usage). Implements from a design file without a pixel-perfect fight, and flags when the spec is ambiguous.
- **React / TypeScript:** Components with clear state, effects, and data fetching. Types the public surface of what they ship. Does not invent a new framework.
- **Quality:** Tests the behaviour they own; uses existing CI; leaves the PR reviewable. Debugging in the browser (network, accessibility tree, performance when it matters) is routine.
- **Product:** Breaks a story into mergeable slices. Explains a trade-off (iterate now vs scale later) without a slide deck.
- **Ownership:** Integrates with APIs and patterns the client already runs. Gives usable review comments, not only “LGTM.”
- **Tooling:** Git without a babysitter. Some Node. Some observability on the path they touch. Uses the client’s AI coding tools without pasting secrets or skipping review.
- **Mentoring:** Can pair a ramping engineer through a web task. Not their full-time job.

Nice-to-haves on a public posting (SEO, extra backend, Kubernetes, native mobile) are not blockers on this global bar. Missing them is only a problem if the core bar above is also thin.

## Typical hiring process

A typical process for a mid-level front-end seat, when the client has not published their own:

1. CV screen (TalentLens) — recommend or not recommend sending the applicant to the client
2. Recruiter / talent-acquisition call
3. Hiring manager, often with product
4. Design / problem-solving with engineers
5. Code review or take-home
6. Live pairing
7. Leadership conversation, then offer

The client’s public posting may define a different sequence. Use that sequence when it is written down. Screening CVs is always the first step: applicants who pass screening are contacted by the client to start this process.

## Screening output

TalentLens does not hire. For each CV, choose **recommend** or **not recommend** to send to the client. Do not invent a third bucket such as hold, reject, or needs more info when a similar profile already has notes in prior matches.
