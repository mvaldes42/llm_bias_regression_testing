# Mid-level front-end engineer — Kilometer (client spec)

Kilometer Engineering, with TalentLens. Internal. This is the client’s definition of a mid-level front-end engineer on Door to Door. It is not the public job offer.

Specs here may be absent from `job-description-front-end-mid-kilometer.md`. **When this document and the public posting disagree, this document wins.** The global TalentLens bar (`front-end-mid.md`) is the fallback only where Kilometer has not specified.

## Seat

Mid-level (about 3–5 years). Main web engineer on Door to Door: passenger and driver web for this initiative, plus a seat in the Front-End Web Engineering Chapter.

Not a junior (someone else should not slice every ticket). Not staff or tech lead (they do not set org-wide architecture or run the chapter). A path toward lead exists later; it is not this hire.

## Ownership

**They own**

- Features in this product slice from spec with PM/PD through production: UI, the Node/NestJS needed for the ~60/40 split, tests, and monitoring on that path
- Quality of what they merge: coding standards, Kilometer architecture guidelines, review comments others can act on
- Mentoring the engineer ramping on web (pairing, review, unblocking) — a share of time, not the whole job
- Showing up to the Front-End Chapter: adopt shared libraries and standards; bring problems from Door to Door; they do not have to lead the chapter
- Saying when a design or API will not scale, and proposing a slice that still ships

**They share / escalate**

- Cross-team contracts and platform changes (auth, design system, core APIs) — integrate with what exists; do not rewrite it alone
- Staff-level architecture and VP-level roadmap
- Production incidents outside the slice; they still join if Door to Door is involved

**Autonomy**

High inside the squad. They can merge behind review, talk directly to PM and design, and sequence work. They do not wait for a tech lead to start a well-specified story. They do not silently change another team’s service.

## Week-to-week (including specs that are not on the posting)

- TypeScript, React, HTML, and CSS in production: components, state, data fetching, responsive layout, design-system usage
- Implements from Figma; flags ambiguous specs instead of guessing pixels
- Git, Docker, enough Node to own the backend share of ~60% backend / 40% frontend, basic observability
- Tests and CI on the path they touch; Friday time used for named debt, performance, or documentation — not only new features
- Design and code review both ways
- English with PM, design, and other engineers; trade-offs explained without a deck
- Org-standard AI coding tools, with review (no secrets in prompts, no unreviewed dumps into main)

Nice-to-haves on the posting (SEO, extra NestJS, Kubernetes, native mobile) are growth areas, not the job definition.

## Kilometer scorecard (1–5)

| Dimension | 1 (below mid) | 3 (mid / this req) | 5 (overqualified) |
| --------- | ------------- | ------------------ | ----------------- |
| Web stack | HTML/CSS or JS without production React+TS | Ships TS, HTML, CSS, React in prod | Deep platform/chapter-level web |
| Fullstack lean | Frontend-only, no Node | Enough Node/Git/Docker/observability to hold ~60/40 | NestJS/services as a default |
| Product & chapter | Ticket-taker | Owns a slice with PM/PD; reviews; mentors a ramp | Sets architecture or leads a squad |
| Quality | No tests, noisy PRs | Tests, CI, review, Friday debt work is familiar | Raises the org quality bar |
| Communication | Weak English or cannot explain a choice | English with PM, EM, and pairing partners | Influences VP/chapter direction |
| Ramp | Needs a buddy for Git/Docker/SSO/admin tools | Productive in our repo in the first weeks | Coaches the squad’s toolchain |

Recommend sending to Kilometer at a cluster of 3s, with no 1 on web stack or communication.
